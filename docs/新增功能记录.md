# 追剧APP 新增功能记录

> 本文档记录追剧APP（zhuiju）版本迭代过程中新增功能的全生命周期信息，包括需求、设计、开发、测试、上线及回滚等环节。

---

## 1. 文档说明

### 1.1 文档目的

本文档用于系统化记录追剧APP在版本迭代过程中所有新增功能（含优化、修复）的需求来源、技术方案、开发进度、上线状态及变更影响，达到以下目的：

- 建立统一的新增功能登记与追踪机制，避免需求遗漏或重复开发；
- 沉淀功能的技术方案与设计决策，便于后续维护与回溯；
- 提供版本规划全景视图，支撑产品、研发、测试、运营多方协同；
- 为功能上线、回滚、影响评估提供标准化依据，降低发布风险。

### 1.2 适用范围

| 项目 | 说明 |
| --- | --- |
| 适用项目 | 追剧APP（zhuiju）Android 原生视频播放客户端 |
| 技术栈 | Kotlin + Jetpack + ExoPlayer + FFmpeg + DanmakuFlameMaster + OkHttp + AES-128-CBC |
| 适用人员 | 产品经理、Android 开发、测试工程师、运维/发布、项目负责人 |
| 适用阶段 | V1.0 基线及后续所有迭代版本（V1.1 / V1.2 / V2.0 及以上） |
| 更新频率 | 每次需求评审、版本规划、功能上线后即时更新 |

### 1.3 术语约定

- **功能ID**：唯一标识一个功能项，规范为 `FEAT-{版本号}-{三位序号}`，例如 `FEAT-V1.0-001`。
- **功能类型**：新增 / 优化 / 修复。
- **状态**：规划中 / 评审通过 / 开发中 / 测试中 / 待上线 / 已上线 / 已回滚 / 暂停。

## 2. 新增功能管理流程

新增功能从提出到上线遵循以下标准化流程，任一阶段未通过则回流至前一阶段修订。

### 2.1 流程图（文字版）

```
需求提出 → 需求评审 → 技术设计 → 开发实现 → 测试验证 → 上线发布 → 线上监控
   ↑           ↓          ↓          ↓          ↓          ↓          ↓
 反馈回流    通过/打回   方案评审   代码评审   测试报告   灰度/全量   异常回滚
```

### 2.2 流程说明

| 阶段 | 责任人 | 输入 | 输出 | 关键动作 |
| --- | --- | --- | --- | --- |
| 1. 需求提出 | 产品经理 / 业务方 | 用户反馈、市场调研、竞品分析 | 《功能登记条目》（本文档表格） | 填写功能ID、名称、描述、优先级、所属版本 |
| 2. 需求评审 | 产品 + 研发 + 测试 | 功能登记条目 | 评审结论（通过/打回/暂缓） | 评估价值、可行性、优先级，更新状态为"评审通过" |
| 3. 技术设计 | Android 开发 | 评审通过的需求 | 技术方案、涉及模块、接口设计 | 评估对现有模块影响，输出技术方案与验收标准 |
| 4. 开发实现 | Android 开发 | 技术方案 | 代码 + 自测报告 | 编码、自测、提交代码评审，状态置"开发中" |
| 5. 测试验证 | 测试工程师 | 开发自测通过的包 | 测试报告、缺陷清单 | 功能测试、回归测试、兼容性测试，状态置"测试中" |
| 6. 上线发布 | 发布工程师 | 测试通过的发版包 | 上线公告、版本号 | 灰度 → 全量，填写实际上线日期，状态置"已上线" |
| 7. 线上监控 | 运维 + 产品 | 线上数据、崩溃日志 | 监控报告 | 关注崩溃率、ANR、播放成功率，异常触发回滚预案 |

### 2.3 阶段流转规则

- 优先级为 `高` 的功能可并行进入设计与开发，但上线仍需测试通过；
- 优先级为 `低` 的功能可在版本排期紧张时顺延至下一版本；
- 任何阶段发现重大风险，需在本文档对应条目"状态"字段标注，并补充风险说明。


### 3.2 字段填写规范

| 字段 | 规范 |
| --- | --- |
| 功能ID | 全局唯一，版本号与所属版本一致，序号在该版本内自增 |
| 功能名称 | 不超过 15 字，动宾结构优先（如"投屏播放"） |
| 优先级 | 高=阻塞版本发布；中=版本内必须完成；低=可顺延 |
| 技术方案 | 需写明依赖的第三方库、关键接口、数据存储方式 |
| 涉及模块 | 对应代码模块名，多个用顿号分隔 |
| 验收标准 | 至少 2 条可验证项，避免主观描述 |

## 4. 版本规划路线图

### 4.1 路线图总表

| 版本号 | 计划时间 | 核心功能 | 状态 |
| --- | --- | --- | --- |
| V1.0 | 2025-Q3 | 基线版本：长视频点播、短视频、本地视频、弹幕、缓存、加密、五大主页 | 已上线 |
| V1.1 | 2025-Q4 | 投屏、4K画质、弹幕屏蔽规则、视频下载、播放历史、收藏夹分组 | 规划中 |
| V1.2 | 2026-Q1 | 直播、弹幕互动表情、倍速微调、AB循环、字幕支持、画中画 | 规划中 |
| V2.0 | 2026-Q2 | AI推荐、创作者中心、视频上传、社交互动、多端同步 | 规划中 |

### 4.2 版本目标说明

- **V1.0**：完成商用级视频播放APP的最小可用基线，覆盖点播、短视频、本地、弹幕、加密等核心场景。
- **V1.1**：围绕"播放体验增强"与"内容留存"扩展，提升用户观看时长与留存率。
- **V1.2**：拓展内容形态（直播）与精细化播放控制，补齐字幕、PiP等播放器基础能力。
- **V2.0**：向内容生态与社交化演进，引入AI推荐与UGC，完成从工具到平台的转型。

## 8. 功能回滚预案

### 8.1 回滚触发条件

满足以下任一条件，立即启动回滚：

| 触发条件 | 阈值/说明 |
| --- | --- |
| 线上崩溃率飙升 | 崩溃率 > 1% 且持续 10 分钟 |
| 核心 ANR 高发 | ANR 率 > 0.5% 且持续 10 分钟 |
| 播放成功率骤降 | 播放成功率 < 95% |
| 加密/解密异常 | 加密视频无法播放，影响主流程 |
| 资源/接口不可用 | 新功能依赖的服务端接口 5xx 持续 |
| 严重资损/舆情 | 出现付费用户投诉或媒体负面 |

### 8.2 回滚流程

```
监控告警 → 值班同学确认 → 通知产品/负责人 → 决策回滚 → 执行回滚 → 验证恢复 → 事后复盘
   ↓            ↓              ↓              ↓            ↓            ↓            ↓
 自动告警    人工核实       10分钟内决策   选择回滚策略   执行对应策略  线上验证    补充文档
```

### 8.3 回滚策略

| 策略 | 适用场景 | 操作方式 | 影响范围 | 预计耗时 |
| --- | --- | --- | --- | --- |
| 远程开关降级 | 功能有 FeatureFlag | 服务端下发关闭开关，客户端禁用入口 | 仅新功能不可用 | <5 分钟 |
| 灰度比例回退 | 灰度阶段异常 | 将灰度比例调回 0% | 灰度用户恢复旧版 | <10 分钟 |
| 热修复补丁 | 代码级缺陷可热更 | 下发 Tinker/Robust 补丁 | 修复后无需发版 | 30~60 分钟 |
| 应用商店回退版本 | 严重问题无法热更 | 上架上一稳定版本包 | 全量用户回退 | 2~4 小时（受审核影响） |
| 服务端回滚 | 服务端接口异常 | 服务端回滚接口版本 | 相关功能降级 | 视服务端流程 |

### 8.4 回滚后处理

1. 在本文档对应功能条目"状态"字段标注为"已回滚"，并补充回滚原因与时间；
2. 48 小时内输出《事故复盘报告》，包含根因、影响、改进措施；
3. 缺陷修复后重新走【新增功能管理流程】，更新状态为"开发中"；
4. 重新上线时灰度比例从最低档重启，不可直接全量。
